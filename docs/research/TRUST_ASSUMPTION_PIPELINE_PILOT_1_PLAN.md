# Trust-assumption pipeline pilot 1

The selected item is ACTIVE for source/reuse and protocol preparation.

## Question and scope

Do two supported Lean reporting paths preserve the exact transitive assumptions
of six fixed fixtures spanning pure logic, explicit axioms, logical axioms,
sorry and native evaluation? Can a report consumer distinguish successful
checking under assumptions from permission to use those assumptions?

The local asset is an executable assumption-preservation matrix and a strict
permission/report regression. It is not a soundness test or checker ranking.

## Gates and execution

First inspect and bind exact primary implementation sources, retained axiom and
Comparator capabilities, and installed toolchain dependencies. Freeze the six
fixture meanings, exact expected sets, two supported paths, negative allowed-set
comparison and safety controls in protocol.json. Independently review these
expectations before any scientific launch. Commit plan, work record, protocol,
source/fixture/tooling manifests and focused tests before fixture compilation.
Generated .olean bytes must be bound before the downstream import observation.
Each attempt has fresh raw evidence and exact scientific/tooling/source inputs.
One launch owner uses the existing positive-RSS gated supervisor. Launches have
120-second time and 2-GiB RSS safety limits; faults require same-item diagnosis
and repair. Counts and elapsed time are observations, never stop conditions.
Tooling repairs retain old attempts and use a new exact revision.

## Closure

permission comparisons, or document a genuine authority/input/capability
boundary after feasible repairs. Preserve all disagreements and report the
limited mechanism measured. Run focused regression, affected validators and the
complete current/historical full-payload repository suite. Refresh current state
through scripts/refresh-current-state. Record scoped result, recommendation and
project-wide comparison, select the highest-value feasible next READY item, and
